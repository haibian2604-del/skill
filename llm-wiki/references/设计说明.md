# 设计说明（为什么这样搭）

> 本文件解释知识库每个设计选择背后的理由。当需要向用户解释、或要为某个新知识库做取舍时读它。

## 1. 三层架构的分工

Karpathy LLM Wiki 的核心判断：**把"不可变的原始资料"和"可演化的理解"分开存**。

| 层 | 谁写 | 可变性 | 类比 |
|----|------|--------|------|
| `00-Raw/` | 用户 + LLM 只移动 | 内容冻结 | 源码依赖（第三方库） |
| `01-Wiki/` | LLM 全权 | 持续演化 | 自己写的代码 |
| `02-Rules/` | 用户 + LLM 共演进 | 极少变 | 代码规范 / lint 配置 |

不做这个分层会怎样：LLM 直接改原始文章 → 原文里的错、过时结论被悄悄"修正"，溯源断裂，用户无法判断哪些是原文、哪些是 LLM 加工。

## 2. 为什么原始资料"内容不可改，但允许搬家"

- 不可改：保证 `sources:` 链回的东西永远是可核验的原文。二次加工内容（LLM 补写的答案、纠错）必须留在 wiki 层并显式标注
- 可搬家：源会不断增长。全平铺在 `00-Raw/` 根目录，几十篇之后就找不到了；按知识点分文件夹是唯一能低成本维持可导航性的做法
- 代价：搬家会让 `[[00-Raw/...]]` 链接失效 → 因此"移动后必须同步改链"写成了铁律

## 3. 为什么 wiki 层目录按"页面类型"而不是按"主题"分

- 按主题分目录会逼出 `tech/llm/frameworks/langchain/` 这类深层嵌套，分类边界立即争议不断，且一个页面只能落一个目录
- 按类型分（summaries / entities / concepts）目录稳定、不会长大；主题用 frontmatter 的 `domain` + `tags` 表达，一个页面可挂多标签，靠 Dataview 做任意视图
- 一句话：**目录管类型，标签管主题**

## 4. 三类页面的职责边界

| 类型 | 回答的问题 | 生命周期 |
|------|-----------|----------|
| summary | "这篇材料讲了什么、与已有知识什么关系" | 与源一一对应，几乎不删 |
| concept | "这个概念是什么、机制、边界" | 多源叠加，越用越厚，是 wiki 的主要资产 |
| entity | "这个东西是什么、有哪些关键事实" | 随事实更新，带时间线 |

判断口诀：**每篇源必产出一篇 summary；summary 里出现的人/组织/产品 → entity；出现的理论/术语/方法 → concept。**

## 5. 为什么强制 frontmatter 与"每页必标 domain"

- 没有 frontmatter，wiki 就退化成"一堆 markdown 文件夹"，无法聚合、无法筛选、无法自动生成目录
- `domain` 必填且唯一 → 保证任何页面都能被至少一种方式聚合浏览；`tags` 负责细粒度
- `status`（seedling/growing/mature）让人一眼看出页面的成熟度，避免把只有两行的占位页当结论用
- `sources` 是溯源链，也是 lint 时检查死链的抓手

## 6. 为什么把"看不见的约定"写进 02-Rules

LLM 每次会话都是无状态启动的。约定若只存在于用户脑子里或对话历史里，换一个会话就丢失。把它写成文件，等于给知识库装了一份可执行的 lint 配置——**`02-Rules/` 的存在价值就是让一致性不依赖记忆**。

配套做法：
- 根目录放一份 `AGENTS.md` 速览，任何代理进场先被它拦住
- 规则文件和用户一起演进；发现更好用的约定就补进去

## 7. Obsidian 侧为什么这样配

- **CSS 片段（wiki-colors.css）**：用颜色把抽象分类变成视觉信号（类型按目录、domain 按标签），浏览时不需要读 frontmatter 就能感知结构
- **graph.json 双层策略**：标签组在前 → 同主题的摘要/概念/实体聚成"主题簇"；路径组在后兜底 → 保证不出现无色的孤儿节点
- **hex vs 十进制 rgb**：CSS 用 hex，Obsidian 图谱配置存十进制 rgb，两处必须同步维护，否则标签有色、图谱没色
- **workspace.json 被 gitignore**：它记录窗口布局等易变 UI 状态，提交上去只会制造无意义 diff

## 8. 适配非技术领域

模板默认词表偏技术（tech 为主），但机制与领域无关：

- `domain` 词表按领域替换（如研究库：`paper` / `dataset` / `method` / `实验室动态`）
- `00-Raw` 知识点文件夹按该领域的主题簇命名
- 三类页面同样适用：论文 → summary；作者/机构/模型/数据集 → entity；方法/指标/概念 → concept
- 颜色表与图谱组随之调整，其余规则不动

## 9. 已知边界

- Obsidian 原生图谱**不支持给边/关系类型单独染色**，只能全局统一色；想区分关系类型，靠 `showTags`、图谱搜索筛选、CSS 按目录着色三种替代手段
- 图谱与 CSS 的配色需**手工保持同步**，新 tag 要两处都登记
- `index.md` 的 Dataview 表格依赖插件，未安装时自动降级为手工条目（这也是为什么手工条目必须维护）
- 单库规模大了（数千页）后，`index.md` 手工维护会吃力 → 引入 qmd 一类的本地检索工具
