# 全栈项目 → 简历项目经历

读一个真实存在的项目代码库，把「代码里的事实」翻译成「招聘方想看的项目经历」：
**项目名称 / 项目地址 / 开发时间 / 技术栈 / 核心模块（核心点）** 五要素齐全，
一次产出**简洁版、均衡版、详细版**三套文案，供用户按简历版位挑选。

## 核心原则

1. **不编造**。数字（用户量、QPS、性能提升）必须有出处：git、README、代码注释、用户口述。无出处一律用 `[待补充：xxx]` 占位符并集中列出，禁止虚构——简历上的每个数字面试都会被问到。
2. **写"我"不写"我们"**。单人项目天然成立；多人项目把成果落到个人动作上（git 作者分布是线索，拿不准就问用户角色分工）。
3. **核心点 > 功能清单**。"核心模块"写有技术含量的部分（认证鉴权、实时通信、支付、缓存、搜索、部署流水线…），不逐条罗列 CRUD。"登录注册"只有在前端做出 SSO/多端免登、后端做出 RBAC 时才值得写细节。
4. **技术是手段，效果是目的**。每条要点尽量回答"所以呢"——性能、稳定性、体验、成本、交付效率。

## 工作流程

### Step 1 · 定位项目

项目路径按优先级取：用户明确指定的路径 > 当前会话工作目录 > 最近上下文里提到的仓库。确认目标是代码库本体（含 `package.json`/`requirements.txt`/`go.mod` 等任一），不是文档目录。

### Step 2 · 一键采集项目事实

```bash
python3 <本技能目录>/scripts/scan_project.py <项目路径>
```

脚本一次给出：**项目地址**（git remote）、**开发时间**（git 首末提交年.月）、技术栈（标记文件 + 依赖级框架识别）、中间件线索、目录结构、README 摘要、包管理文件关键字段。仅依赖 Python 标准库。

### Step 3 · 精读核心模块，提炼核心点

脚本只能定位，不能理解。从目录结构挑 **3-6 个核心模块**，用 Read 精读路由/控制器/服务层/数据模型/核心页面，每个模块确认两件事：

- **职责**：这个模块解决什么业务问题（一句话）
- **核心点**：里面有什么值得上简历的技术决策或亮点

全栈项目按「前端亮点 / 后端亮点 / 数据与部署亮点」三个侧面各找 1-2 个，避免只写一端。常见核心点清单：JWT/OAuth 鉴权、RBAC 权限、WebSocket 实时推送、支付对账、文件上传（OSS/分片）、缓存策略、分页与搜索优化、定时任务、Docker/CI-CD、单元测试。

判断标准：**需要查资料、做选型、调方案的问题才算核心点**；脚手架自带、照文档抄的不算。

### Step 4 · 补齐信息缺口

六要素里脚本拿不到的，**一次性列出追问**（表格形式：字段 / 为什么要 / 示例值，不超过 5 条），不要挤牙膏：

| 缺口 | 处理 |
|------|------|
| 项目地址（无 git remote） | 追问：GitHub/Gitee 链接或"暂不公开" |
| 开发时间（非 git 仓库） | 追问起止年月 |
| 个人角色（多人项目） | 追问分工，避免把他人工作写成自己的 |
| 量化数据 | 用户说不出就占位符，不强求 |

用户表示"先出稿"时，全部走占位符继续生成，文末集中列待补清单。

### Step 5 · 生成三版本文案

严格按 `references/writing-guide.md` 的规格与模板输出。三版差异速览：

| 版本 | 篇幅 | 适用场景 |
|------|------|----------|
| 简洁版 | 定位 1 行 + 要点 2-3 条 | 简历空间紧张、多项目并列 |
| 均衡版 | 定位 1-2 行 + 要点 4-5 条 | **默认推荐**，标准校招/社招简历 |
| 详细版 | 背景 2-3 行 + 要点 6-8 条（含难点与解法） | 项目经历为主打、单项目深挖 |

三版共用同一个「项目信息」头部（名称/地址/时间/技术栈），只是正文详略不同。要点的写作公式、好差对照示例、量化占位符规范都在 writing-guide 里，动笔前先读它。

### Step 6 · 落盘交付

写入 `<项目路径>/project-resume.md`（用户指定了其他位置则遵从），结构：

```markdown
# 项目经历 · <项目名>
> 生成自 <项目路径> · 2026-09-29
## 项目信息（三版共用）
## 简洁版
## 均衡版
## 详细版
## 待补充清单（如有占位符）
```

交付时告知用户：文件位置、推荐用均衡版、占位符需要本人补数。
