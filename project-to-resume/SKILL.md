# 项目材料 → 简历项目经历

## 用途

把"工程师视角的项目事实"翻译成"招聘方视角的项目经历"：突出个人贡献、技术难点与可量化结果，而不是罗列功能清单或技术名词。

## 核心原则

1. **不编造数据**。任何数字（QPS、耗时、团队规模、用户量、性能提升）必须有来源：用户口述、README、监控截图、代码注释。无来源的一律走"追问"或"占位符"，禁止虚构。
2. **写"我"不写"我们"**。团队成果要落到个人动作上：我负责的模块、我做的设计决策、我解决的具体问题。
3. **技术是手段，结果是目的**。每条经历必须能回答"所以呢"——性能提升、成本下降、稳定性提升、业务指标改善、交付周期缩短。
4. **宁可少写，不可泛写**。3 条有细节的经历 > 6 条正确的废话。

## 工作流程

### Step 1 · 收集输入

按输入形态分别处理：

| 形态 | 处理方式 |
|------|----------|
| 本地代码仓库/目录 | 先运行 `scripts/scan_project.py <路径>` 拿到技术栈与结构摘要，再按需 Read 关键文件（README、入口文件、核心模块、配置） |
| **HTML 架构图页面** | 先运行 `scripts/extract_diagram.py <html 路径>` 抽取节点与链路；脚本解不出时按下方「HTML 架构图处理」降级处理 |
| 架构图/流程图图片 | 用 Read 工具直接读取图片识别组件与链路；识别不清时向用户确认关键节点名称 |
| PDF / Word / PRD | 先转成文本（PDF 用 Read 或 pdf 技能），抽需求背景与模块划分 |
| 口述 / 零散描述 | 直接进入 Step 2，按字段表追问缺口 |

多个输入可合并，例如"仓库 + 架构图"。

#### HTML 架构图处理

架构图常以 HTML 页面交付（draw.io 导出、Mermaid 渲染页、ECharts/AntV 拓扑页、手写布局页、带 JS 的交互页）。优先级：

1. **本地 HTML 文件** → `scripts/extract_diagram.py <路径>`，脚本自动识别并解析：

   | 页面类型 | 抽取方式 | 拿到什么 |
   |----------|----------|----------|
   | draw.io / diagrams.net 导出 | 解压 `mxfile` 的 deflate+base64 数据（含 `data-mxgraph` 属性与 `<diagram>` 直嵌两种） | 节点名 + 带标签的连线关系 |
   | Mermaid | 解析 `flowchart/graph` 源码 | 节点名（自动把 `A[订单服务]` 还原为"订单服务"）+ 链路 |
   | ECharts / G6 / X6 / D3 | 正则提取 `option` 中的 `name`、`source/target` | 节点名 + 链路（尽力而为） |
   | 内联 SVG | 提取 `<text>` / `<title>` / `aria-label` | 节点名（无链路） |
   | 纯 HTML 布局 | 去掉 script/style 后提取可见文本 | 节点名（无链路） |
   | 只有 `<img src="arch.png">` | 脚本报出图片路径 | 改用 Read 读图片 |

2. **输出结果为空**（页面靠 JS 动态渲染，单文件 bundle 或框架页）→ 用 agent-browser 或 playwright 技能打开页面截图，再用 Read 读截图识别；也可用它们 dump 渲染后的 DOM 文本再喂给脚本思路处理。
3. **只有 URL（如 localhost:3000）** → 先 `curl -L <url> -o /tmp/arch.html` 存成本地文件再跑脚本；若页面必须 JS 渲染，走第 2 条。

抽取到的只是**图上可见的组件与链路**，仍需向用户确认：哪部分是自己做的、各层职责、规模与量化结果。禁止把图上的组件当成"我负责的模块"。

### Step 2 · 抽取项目事实

按 12 个字段结构化整理（字段说明见 `references/writing-guide.md`）：

```
项目名 / 一句话定位 / 起止时间 / 我的角色 / 团队规模
技术栈 / 整体架构与数据流 / 我负责的模块
技术难点（≤3 个）/ 对应解法 / 量化结果 / 业务价值
```

难点筛选标准：真正需要查资料、做选型、调参数、改方案的问题才算难点。CRUD 拼接、常规接口开发不算。

输入含架构图时：把抽取到的节点归入「接入层 / 业务层 / 中间件 / 存储层 / 基础设施」，链路写成"谁 → 谁（协议或数据）"。分层结构即"整体架构与数据流"字段的填充内容。

### Step 3 · 补齐信息缺口

**阻塞项（必须追问，缺失则无法下笔）**
- 我的角色与实际负责模块（避免把他人工作写成自己的）
- 项目规模量级（用户量 / 数据量 / QPS 至少一项）
- 至少 1 个可量化结果（性能、稳定性、成本、效率、业务指标任一）

**可推断项（基于技术栈合理推断，输出时标注，供用户核对）**
- 架构分层、中间件选型理由、常见性能瓶颈

追问方式：一次性列出清单（不超过 5 条），用表格给出"字段 / 为什么要 / 示例值"，不要逐条挤牙膏。用户明确表示"没有数据"或"先出稿"时，改用 `[待补充：xxx]` 占位符继续生成，并在文末集中列出待补清单。

### Step 4 · 按 JD 定制（可选）

用户提供 JD 时：
1. 抽取 JD 高频技术词与能力要求（≤8 个）
2. 把项目事实中能对应的点提到前两条，使用 JD 的原词表述
3. JD 要求但项目里没有的：**不硬凑**。在文末"面试准备提示"标注为风险点，提示用户准备说辞或重新评估是否投递

未提供 JD → 产出通用技术岗版本。

### Step 5 · 生成输出

严格按固定 Markdown 模板产出（格式细则见 `references/writing-guide.md` 第一节）：

```markdown
## 项目经验
### 项目名 \| 角色
2025\-10 \~ 2025\-12
项目地址：\[url\]\(url\)        # 无链接则整行省略
**项目简介**：架构/技术底座 + 业务范围 + 场景特征，一句
**技术栈**：顿号分隔，6–10 个
核心工作与成果：
1. 能力点命名：技术手段与做法，结果；
2. ……（4–6 条，每条以分号结尾）
```

要点：
- `|` 转义为 `\|`，日期区间用 `\~`，链接写成 `\[url\]\(url\)` 且 URL 中的 `.` 转义
- 条目不写主语（默认是"我"），冒号前是 4–10 字能力点命名，冒号后是「手段，结果」
- 结果量化优先；无数字时写可验证的定性收益（"查询效率提升一个数量级"），不写"效果良好"
- 多项目时全部挂在同一个 `## 项目经验` 下，按时间倒序

配套产出（同一文件内，附在正文之后）：
- **精简版**：同一模板，条目压到 2–3 条，用于简历空间紧张
- **深度版**：1 段面试口述稿，200–300 字，补选型对比与权衡，不写进简历正文

然后：
- 在对话中直接输出正文全文（可直接复制）
- 写入 `项目经历-<项目名>.md`（默认当前工作目录，用户可指定路径），骨架用 `assets/output-template.md`
- 文末附「待补充数据清单」与「面试追问预判」（3–5 个可能被深挖的点）
- 用 present_files 展示生成的 md 文件

## 写作规范

句式模板、动词库、量化维度、按岗位侧重点映射、常见反模式见 `references/writing-guide.md`；完整 before/after 案例见 `references/examples.md`。生成前先读 `references/writing-guide.md`。

## 红线

- 禁止虚构任何数字、公司名、职级、时间
- 禁止把团队成果写成个人成果而不加限定
- 禁止堆砌技术名词无因果（"使用 Redis+Kafka+微服务实现了…"但不说为什么）
- 禁止出现"参与"、"负责相关工作"、"熟悉运用"等无信息量表述
- 单个项目的核心工作与成果控制在 4–6 条，超过 6 条必须合并同类项

## 脚本

`scripts/scan_project.py <项目路径>` — 纯标准库，无依赖。输出技术栈推断、目录结构摘要、README 前 40 行、包管理文件关键字段、git 提交统计。用于快速建立项目事实，再精读核心模块。

`scripts/extract_diagram.py <html 路径> [--json]` — 纯标准库，无依赖。从 HTML 架构图抽取节点与链路，支持 draw.io（自动解压）、Mermaid、ECharts/G6/X6、内联 SVG、纯 HTML 布局；页面依赖 JS 渲染时结果为空，需改用浏览器截图。
