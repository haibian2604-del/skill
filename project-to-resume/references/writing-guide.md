# 简历项目经历写作规范

## 一、12 个字段说明

| 字段 | 说明 | 抽取来源 |
|------|------|----------|
| 项目名 | 对外可理解的名字，避免内部代号 | README、PRD 标题 |
| 一句话定位 | 「给谁 + 解决什么 + 用什么方式」，20 字内 | README 首段 |
| 起止时间 | 精确到月 | 用户口述、git log |
| 我的角色 | 负责人 / 核心开发 / 模块 owner | 用户口述、git 贡献统计 |
| 团队规模 | 总人数 + 分工（前后端各几人） | 用户口述 |
| 技术栈 | 语言、框架、中间件、存储、部署 | scan_project.py、配置文件 |
| 架构与数据流 | 请求从入口到存储的完整链路 | 架构图、入口文件 |
| 我负责的模块 | 具体模块名 + 边界 | 用户口述、git 提交范围 |
| 技术难点 | ≤3 个，需真正耗时解决的问题 | 用户口述、TODO/注释/issue |
| 解法 | 选型理由 + 关键实现 + 权衡 | 用户口述、代码 |
| 量化结果 | 性能、稳定性、成本、效率、业务指标 | 监控、压测报告、用户口述 |
| 业务价值 | 上线后带来的变化 | PRD 背景、复盘文档 |

## 二、句式模板

### 标准条目（80–150 字）

```
[动作动词] + [模块/系统] + [技术手段] + ，解决 [具体问题] + ，使 [指标] 从 [A] 降至/提升至 [B]（[百分比]）。
```

示例：
> 针对订单查询在大促期间响应抖动问题，设计「本地 Caffeine 缓存 + Redis 分布式锁 + 空值占位」三级防穿透方案，将缓存击穿导致的 DB 峰值 QPS 从 1.2 万压至 800，P99 延迟由 1.8s 降至 120ms。

### 难点三元组

```
难点（一句话现象）→ 解法（选型 + 关键动作）→ 结果（数字）
```

三元组必须连写，拆开就失去说服力。

### 项目头（放在第一版条目前）

```
项目名称｜角色｜时间
技术栈：xxx
一句话定位：xxx
```

## 三、动词库（按场景）

| 场景 | 强动词 |
|------|--------|
| 性能优化 | 优化、重构、压测、定位瓶颈、削峰、降延迟、提升吞吐 |
| 架构设计 | 设计、拆分、抽象、解耦、收敛、统一、落地 |
| 稳定性 | 兜底、降级、限流、熔断、容灾、灰度、可观测性建设 |
| 效率/工程 | 自动化、标准化、沉淀、搭建、收敛流程、缩短交付周期 |
| 数据/算法 | 建模、清洗、特征工程、调优、评估、上线 AB 实验 |
| 业务 | 支撑、承接、覆盖、提升转化、降低资损 |

禁用弱动词：参与、协助、配合、熟悉、了解、负责相关工作、完成领导交办。

## 四、量化维度清单（按优先级）

1. **性能**：P99/P95 延迟、QPS、TPS、耗时（ms→ms）
2. **规模**：日活、数据量、日订单、存储量、节点数
3. **稳定性**：可用性（99.9x%）、故障次数、MTTR、告警量下降
4. **效率**：发布时间从 X 到 Y、人工工时节省、自动化覆盖率
5. **成本**：机器数、云账单、资源占用下降
6. **业务**：转化率、留存、GMV、资损金额、客服工单量

没有绝对值就用相对值（"下降 60%"），没有相对值就写对比基准（"较改造前"）。实在没有 → `[待补充]`。

## 五、按岗位侧重点映射

| 目标岗位 | 前两条该写什么 | 关键词 |
|----------|----------------|--------|
| 后端 | 高并发/高可用设计、存储与缓存、分布式一致性 | QPS、削峰、幂等、分库分表、容灾 |
| 前端 | 性能与体验、工程化、复杂交互实现 | 首屏、LCP、构建耗时、组件复用率、埋点 |
| 算法/ML | 数据、特征、模型、线上效果 | AUC、召回率、AB 实验、推理耗时 |
| 数据 | 链路、时效性、质量、成本 | T+1→实时、数据一致性、任务调度、血缘 |
| 测试/DevOps | 自动化、覆盖率、稳定性、交付效率 | 自动化率、CI 时长、故障恢复、发布频率 |
| 移动端 | 包体积、启动速度、崩溃率、跨端 | 启动耗时、ANR/崩溃率、包体积 |

## 六、常见反模式

| 反模式 | 问题 | 改法 |
|--------|------|------|
| 技术名词堆砌 | 无因果，像 README | 每个技术词后面跟"为了解决什么" |
| 只写职责不写结果 | 看不出能力高低 | 每条补一个数字 |
| 全程"我们" | 分不清个人贡献 | 改成"我"，团队成果写"主导/牵头" |
| 写功能清单 | 像需求文档 | 改成难点与解法 |
| 数字无基准 | "提升 300%" 无说服力 | 补 "从 X 到 Y" |
| 过度包装 | 面试一问就穿帮 | 保留可解释的技术细节 |

## 七、可解释性自检

生成后逐条自问：
1. 这条里的每个数字，面试时能否说清测量方式？
2. 这个技术选型，能否说出放弃了什么、为什么？
3. 这个难点，能否讲出排查过程（怎么发现、怎么定位、怎么验证）？

答不上来的，要么删掉，要么降级为占位符。
