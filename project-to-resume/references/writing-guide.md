# 简历项目经历写作指南

生成三版本文案前必读。本文件包含：要点写作公式、量化规范、三版本详细规格、完整示例。

## 一、要点写作公式

每条要点 = **动词开头 + 具体模块 + 技术手段 + （有效果则加）效果**。

好差对照（同一个事实的两种写法）：

| ❌ 差（功能清单腔） | ✅ 好（工程师腔） |
|---|---|
| 负责用户模块的开发 | 设计并实现基于 JWT + Redis 的登录态管理，支持多端免登与强制下线 |
| 使用了 WebSocket | 基于 Socket.IO 实现订单状态实时推送，替代轮询方案，请求数下降约 90% |
| 参与前端页面开发 | 独立完成 12 个核心页面与组件库封装，统一请求层错误处理与 Loading 规范 |
| 优化了性能 | 通过虚拟列表 + 接口合并将万级数据表格首屏渲染从 3s 降至 600ms |
| 负责数据库设计 | 设计订单/商品/库存 3 大域共 18 张表，用乐观锁解决超卖问题 |

弱动词清单：参与、协助、了解、学习、接触、帮忙。换成：设计、实现、搭建、重构、封装、落地、主导、独立完成。

**注意**：优化类要点必须写"从 X 到 Y"或"替代了什么方案"才有说服力；没有基线数据就写方案本身（"引入虚拟列表支撑万级数据渲染"），不要编百分比。

## 二、量化数据规范

- 有来源的数字直接写：git 提交量、代码规模、页面/接口数量、表数量——这些自己数得出来。
- 无来源的用占位符：`[待补充：日活用户数]`、`[待补充：QPS]`。三版里同一数字用同一占位符，文末集中列清单。
- 团队规模、用户量、性能基线永远不猜。面试官追问"这个 90% 怎么测的"时，用户必须答得上来。

## 三、三版本规格

三版共用同一「项目信息」头部；区别只在正文详略。技术栈一行用 `·` 分隔，按 **前端 → 后端 → 数据库/中间件 → 工具/部署** 排序。

### 简洁版（2-3 条要点，每条 ≤ 40 字）

只保留定位 + 最亮的 2-3 个核心点。写法：第一条合并"项目是什么 + 我做了什么"，其余每条一个核心点。

```markdown
### 简洁版

**社区二手交易平台**（个人全栈项目）｜2024.03 – 2024.09
技术栈：React · NestJS · PostgreSQL · Redis · Docker
- 独立完成前后端开发与部署：商品发布、站内即时聊天、订单支付全流程
- 基于 Socket.IO 实现买卖双方实时聊天与订单状态推送
- Docker Compose 一键部署，GitHub Actions 自动化测试与发布
```

### 均衡版（定位 1-2 行 + 4-5 条要点）——默认推荐

结构：**项目定位行 → 技术栈行 → 要点**。要点排序：架构级/全局性的在前，单模块亮点居中，工程化收尾。每条一个侧面（前端/后端/数据/部署），不重复。

```markdown
### 均衡版

**社区二手交易平台**（个人全栈项目）｜2024.03 – 2024.09
技术栈：React · NestJS · PostgreSQL · Redis · Socket.IO · Docker
- 独立完成从需求拆解、数据库设计到部署上线的全栈开发，含商品、聊天、订单、信用分 4 大模块
- 后端基于 NestJS 分层架构实现 30+ RESTful 接口，JWT 鉴权 + RBAC 权限覆盖买家/卖家/管理员三种角色
- 基于 Socket.IO 实现站内即时聊天与订单状态实时推送，配合 Redis 维护在线状态与未读消息数
- 设计订单超卖防护：PostgreSQL 乐观锁 + Redis 分布式锁兜底，压测下零超卖
- Docker Compose 编排 + GitHub Actions 实现 push 即自动测试、构建、发布
```

### 详细版（背景 2-3 行 + 6-8 条要点，含难点与解法）

多两样东西：**项目背景段**（为什么做、服务谁、规模）和**难点条目**（问题 → 方案 → 结果三段式）。适合项目经历是简历主打、或作品集附页。

```markdown
### 详细版

**社区二手交易平台**（个人全栈项目）｜2024.03 – 2024.09
项目地址：https://github.com/xxx/xxx
技术栈：React · NestJS · PostgreSQL · Redis · Socket.IO · Docker
校园场景二手交易平台：解决微信群刷屏式买卖信息不可检索、无信用保障的问题，
支撑商品发布、检索、站内聊天、担保订单与信用体系，注册用户 [待补充：注册用户数]。
- 独立完成需求拆解、领域建模（用户/商品/订单/信用 4 域 18 张表）到部署运维的全流程
- 前端 React + Antd 实现 [待补充：页面数] 个页面，封装统一请求层（鉴权注入/错误码归一/取消重复请求）
- 后端 NestJS 分层架构，30+ 接口；按域拆分 module，统一响应体、参数校验与日志埋点
- 【难点】高并发下单超卖：最初直接扣库存压测必超卖 → 改为乐观锁版本号扣减，Redis 分布式锁兜底热点商品 → 复测 500 并发零超卖
- 【难点】IM 消息可靠性：Socket.IO 断线重连丢消息 → 引入消息表 + 序列号 + 客户端 ACK 补拉，重连后消息零丢失
- 站内检索从 LIKE 全表扫描迁移至 PostgreSQL 全文索引，千级数据查询从 200ms 降至 20ms
- JWT + Redis 实现多端登录互踢与刷新令牌，管理员侧 RBAC 控制到按钮级
- Docker Compose 一键起全套服务，GitHub Actions 完成测试/构建/镜像推送，部署从手动 30 分钟降至 3 分钟
```

## 四、红线自查（生成后过一遍）

1. 每个数字有出处，或已是 `[待补充]` 占位符？
2. 没有出现"参与/协助/了解"？
3. 每条要点说的都是"我做了什么"，不是"项目有什么"？
4. 三版的技术栈行完全一致（只是正文详略不同）？
5. 没有把 README 里的规划/愿景写成已实现的功能？（README 写了但代码里没有的，宁可不写）
