# 简历项目经历写作指南

生成三版本文案前必读。本文件包含：要点写作公式、量化规范、三版本详细规格、完整示例、红线自查。

## 一、要点写作公式（本技能的心脏）

每条要点必须能还原成一句话：**「因为（什么问题），所以（用什么方法）」**。
方法端写具体机制和数字，问题端写到"什么场景下会坏"。只有一端的条目不合格。

两种条目形态：

**① 总览条**（永远放第一条）：独立/主导 + 交付范围 + 功能覆盖（可带结构性数字，如模块数、表数量）。

> 独立完成需求拆解、架构设计到开发测试的全栈交付，功能覆盖简历上传解析、模拟面试对话、逐题评分、报告生成

**② 核心点条**：方法名（加引号或编号）+ 冒号 + 机制细节 + 解决的问题 / 带来的保障。

> 设计「多 Agent + 纯代码编排器」架构：5 个角色 Agent 各自独立人格、独立 Zod 输出 schema、独立模型配置（生成用廉价模型、评估用强模型）；编排器是唯一事实来源，Agent 间只传递结构化产物

> 实现 LLM 结构化输出三层容错管线：截断 JSON 逐字符修复 → 嵌套病态结构递归抢救 → 带纠错指令重试，解决廉价中文模型无视 JSON Schema 指令的问题，全部逻辑可离线单测

> 面试流程全部由确定性规则驱动（非 LLM 自主决策）：得分 <0.65 触发追问且每题限 1 次、真实模式按难度阶梯渐进出题、连 3 题 <0.40 或均值 <0.45 提前收尾——保证面试节奏可控、可复现

> 基于 Supabase 实现 8 张表的领域建模与 RLS 行级权限；用户自配的 LLM API Key 采用 AES-256-GCM 加密存储、掩码展示

> 面试官流式输出的可靠性设计：tee() 旁路流累积全文不阻塞响应，流中断时落盘部分文本 + 截断标记，刷新页面可原样还原卷面、接续面试进度

注意上面例子里反复出现的写法特征，照着做：

- **机制有内部结构**：三层管线用 `A → B → C` 展开、5 个 Agent 拆出"各自独立什么"；不把方法压缩成一个名词。
- **阈值/配置直接亮出来**：`<0.65`、`每题限 1 次`、`连 3 题 <0.40`、`AES-256-GCM`——数字和规格本身就是可信度。
- **反面标注增加说服力**：`（非 LLM 自主决策）`、`（生成用廉价模型、评估用强模型）`——写清"不是什么"往往正是懂行面试官想看的取舍。
- **结尾落到保障**：`保证节奏可控、可复现`、`全部逻辑可离线单测`、`刷新页面可原样还原`——问题解决后"所以呢"的答案。

好差对照（同一个事实的三个档次）：

| ❌ 功能清单腔 | ❌ 技术名词腔 | ✅ 问题-方法腔 |
|---|---|---|
| 参与面试流程开发 | 面试流程由 LLM 智能驱动 | 确定性规则驱动（非 LLM 自主决策）：<0.65 触发追问限 1 次、难度阶梯出题、连 3 题 <0.40 提前收尾——节奏可控可复现 |
| 实现了输出解析和重试 | 使用 JSON Schema 约束输出 | 三层容错管线：截断逐字符修复 → 病态结构递归抢救 → 带纠错重试，解决廉价中文模型无视 Schema 的问题 |
| 负责数据库设计 | 使用 Supabase + RLS | Supabase 8 张表领域建模 + RLS 行级权限；API Key AES-256-GCM 加密存储、掩码展示，杜绝明文落库 |

第三列才是合格线。"智能驱动""使用了 X"这类写法的问题：方法端看不出怎么做，问题端看不出为什么需要它。

弱动词清单：参与、协助、了解、学习、接触、帮忙。换成：设计、实现、搭建、重构、封装、落地、主导、独立完成。

## 二、量化数据规范

- **结构性数字直接写**：表数量、接口数、页面数、Agent 数量——精读时顺手数，代码里数得出的都是事实。
- **机制参数直接写**：代码里的阈值、超时、加密算法、重试次数——这些是事实，不是吹嘘。
- **无来源的效果数字用占位符**：`[待补充：日活用户数]`、`[待补充：QPS]`。三版里同一数字用同一占位符，文末集中列清单。
- 团队规模、用户量、性能基线永远不猜。面试官追问"这个 90% 怎么测的"时，用户必须答得上来。

## 三、三版本规格

三版共用同一「项目信息」头部；区别只在正文详略。技术栈一行用 `·` 分隔，按 **前端 → 后端 → 数据库/中间件 → 工具/部署** 排序。第一条永远是总览条，核心点条按含金量排序（架构级在前，模块级居中，工程化收尾）。

### 简洁版（2-3 条要点，每条 ≤ 40 字）

只保留总览 + 最亮的 2 个核心点，每个核心点仍是"方法：问题"的压缩形态。

```markdown
### 简洁版

**CampusMarket 校园二手交易平台**（个人全栈项目）｜2024.03 – 2024.09
技术栈：React · Express · Socket.IO · MySQL · Redis · Docker
- 独立完成前后端开发与部署，覆盖商品发布检索、站内聊天、担保订单、信用分四大模块
- 乐观锁 + Redis 分布式锁双层扣减，解决高并发下单超卖
- 消息表 + 序列号 + ACK 补拉，Socket.IO 断线重连聊天零丢消息
```

### 均衡版（总览条 + 4-5 条核心点）——默认推荐

```markdown
### 均衡版

**CampusMarket 校园二手交易平台**（个人全栈项目）｜2024.03 – 2024.09
技术栈：React · Vite · Tailwind CSS · Express · Socket.IO · MySQL · Redis · Docker
- 独立完成需求拆解、领域建模（4 域 18 张表）到部署上线的全栈交付，功能覆盖商品发布检索、站内聊天、担保订单、信用分
- 设计「乐观锁 + 分布式锁」双层库存扣减方案：PostgreSQL 版本号扣减兜底常规并发，Redis 分布式锁串行化热点商品，解决高并发下单超卖问题
- 基于 Socket.IO 实现站内聊天与订单状态实时推送（替代 2s 轮询）：消息表 + 序列号 + 客户端 ACK 补拉，断线重连消息零丢失
- JWT + Redis 实现多端登录互踢与刷新令牌轮换，解决 token 泄露后无法吊销的问题
- Docker Compose 编排 + GitHub Actions 流水线，push 即自动测试、构建、发布
```

### 详细版（背景 2-3 行 + 6-8 条要点，难点条目展开）

比均衡版多两样：**背景段**（为什么做、服务谁、规模）和**难点条目的三段式展开**（问题场景 → 方案 → 结果）。适合项目经历是简历主打、或作品集附页。

```markdown

**CampusMarket 校园二手交易平台**（个人全栈项目）｜2024.03 – 2024.09
```

## 四、红线自查（生成后过一遍）

1. 每条核心点能否还原成「因为 X 问题，所以 Y 方法」？只有一端的：要么补另一端，要么降为一句带过。
2. 方法端有内部结构和数字（几层、几个、阈值多少），而不是一个光秃秃的名词？
3. 每个数字有出处（代码、git、脚本统计、用户口述），或已是 `[待补充]` 占位符？
4. 没有出现"参与/协助/了解"？没有"使用了 X"式的名词堆砌？
5. 第一条是总览条（交付范围 + 功能覆盖）？没有出现代码行数、测试文件数这类码量指标？
6. 没有把 README 里的规划/愿景写成已实现的功能？（README 写了但代码里没有的，宁可不写）
