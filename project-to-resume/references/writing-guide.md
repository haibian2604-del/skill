# 简历项目经历写作指南

生成两版本文案前必读。本文件包含：职责条目公式、量化规范、两版本详细规格、完整示例、红线自查。

## 一、职责条目公式（本技能的心脏）

每条主要职责固定句式：

**「模块名**：针对（什么问题），设计并实现（什么方法）；（机制细节展开），（达成的效果）。」

真实范例（同一句式的五种变体）：

> **Agent 核心引擎**：针对复杂任务单次推理无法完成的问题，设计并实现 Think-Execute 循环机制；通过维护上下文状态与指令解析，支持 Agent 自动进行任务规划与多轮工具调用，确保复杂指令的连贯执行。

> **分层会话记忆管理**：针对长对话超出 LLM 上下文窗口导致早期信息丢失的问题，设计并实现三层记忆架构；按 USER 消息切分轮次，仅将最近 N 轮完整记录作为 LLM 上下文发送，超 20 轮后自动对历史片段生成段落摘要并向量化存储，每轮结束后异步提取关键事实并持久化；新一轮对话启动时自动注入最新摘要与语义检索匹配的相关事实，让 LLM 仍能访问早期关键信息。

> **可扩展工具系统**：针对工具硬编码导致扩展性差的问题，设计实现可扩展的工具调用框架；采用"固定+可选"的配置策略结合动态注入机制，实现工具的按需加载与灵活拼装，新增工具仅需实现标准接口并配置声明，无需改动核心引擎代码。

> **RAG 知识库检索**：针对传统检索缺乏语义理解、知识库接入面窄的问题，基于 pgvector 实现向量相似度搜索；引入文档解析技术处理 PDF/DOCX/Markdown 等多格式文件，通过统一分块策略将文档内容向量化入库，实现多格式文档的"上传即检索"。

> **多模型动态支持**：针对不同大模型 API 协议差异导致切换困难的问题，设计 ChatClientRegistry 注册表模式；通过抽象统一调用接口屏蔽底层差异，实现 DeepSeek、智谱 AI 等多模型的动态路由与按需切换，提升系统灵活性。

句式拆解与写法要求：

- **加粗模块名开头**：2-8 字的功能/机制命名（"分层会话记忆管理"），不是文件名也不是表名——名字本身就是简历上的锚点。
- **"针对……的问题"开头**：问题写到"什么场景下会坏"（长对话超窗口导致早期信息丢失、API 协议差异导致切换困难、高并发超卖）。禁止把问题写成需求（"为了支持多模型"）。
- **"设计并实现……"给方法命名**：Think-Execute 循环、三层记忆架构、ChatClientRegistry 注册表模式——方法要有名字，名字来自代码里的真实设计。
- **分号后展开机制**：通过/采用/引入……，把机制写到"怎么做"的颗粒度（最近 N 轮 + 超 20 轮摘要向量化 + 异步提取关键事实）。
- **结尾落到效果**：确保……、实现……、提升……、无需改动……。
- **中文全角标点**，条目以句号结尾。
- **禁止「——【难点】」式标注**：问题不用标签标出，直接用"针对……的问题"织进句子。

好差对照（同一个事实的三个档次）：

| ❌ 功能清单腔 | ❌ 技术名词腔 | ✅ 问题-方法腔 |
|---|---|---|
| 参与面试流程开发 | 面试流程由 LLM 智能驱动 | **面试流程编排**：针对 LLM 自主决策导致节奏不可控的问题，设计确定性规则引擎；得分 <0.65 触发追问且每题限 1 次、按难度阶梯渐进出题、连 3 题 <0.40 提前收尾，保证面试节奏可控、可复现。 |
| 实现了输出解析和重试 | 使用 JSON Schema 约束输出 | **结构化输出容错**：针对廉价中文模型无视 JSON Schema 指令、输出截断的问题，设计三层容错管线；截断 JSON 逐字符修复 → 病态结构递归抢救 → 带纠错指令重试，全部逻辑可离线单测。 |
| 负责数据库设计 | 使用 Supabase + RLS | **数据建模与安全**：基于 Supabase 完成 8 张表领域建模与 RLS 行级权限；用户 API Key 采用 AES-256-GCM 加密存储、掩码展示，杜绝明文落库。 |

第三列才是合格线。"智能驱动""使用了 X"这类写法的问题：方法端看不出怎么做，问题端看不出为什么需要它。

弱动词清单：参与、协助、了解、学习、接触、帮忙。换成：设计、实现、搭建、重构、封装、落地、主导、独立完成。

## 二、量化数据规范

- **结构性数字直接写**：表数量、接口数、页面数、Agent 数量——精读时顺手数，代码里数得出的都是事实。
- **机制参数直接写**：代码里的阈值、超时、加密算法、重试次数（"超 20 轮生成摘要"、"<0.65 触发追问"）——这些是事实，不是吹嘘。
- **无来源的效果数字用占位符**：`[待补充：日活用户数]`、`[待补充：QPS]`。两版里同一数字用同一占位符，文末集中列清单。
- 团队规模、用户量、性能基线永远不猜。**代码行数、测试文件数这类码量指标不写**——它们不构成招聘方关心的信息。

## 三、两版本规格

两版共用同一「项目信息」头部。技术栈一行用 `·` 分隔，按 **前端 → 后端 → 数据库/中间件 → 工具/部署** 排序。职责条目按含金量排序（架构级在前，模块级居中，工程化收尾）。

### 均衡版（主要职责 4-6 条，完整句式）——默认推荐

```markdown
### 均衡版

**CampusMarket 校园二手交易平台**（个人全栈项目）｜2024.03 – 2024.09
项目地址：https://github.com/xxx/xxx
技术栈：React · Vite · Tailwind CSS · Express · Socket.IO · MySQL · Redis · Docker

- **库存扣减**：针对高并发下单超卖的问题，设计「乐观锁 + 分布式锁」双层扣减方案；常规并发走 PostgreSQL 版本号扣减，热点商品加 Redis 分布式锁串行化，压测下零超卖。
- **可靠消息推送**：针对 Socket.IO 断线重连丢消息、轮询拖垮服务器的问题，基于 Socket.IO 实现站内聊天与订单状态实时推送；引入消息表 + 序列号 + 客户端 ACK 补拉机制，断线重连消息零丢失。
- **登录态管理**：针对 token 泄露后无法吊销的问题，实现 JWT + Redis 登录态方案；支持多端登录互踢与刷新令牌轮换，管理员侧权限控制关键操作。
- **检索优化**：针对 LIKE 全表扫描慢查询的问题，将商品检索迁移至 MySQL 全文索引；查询耗时从 [待补充：优化前] 降至 [待补充：优化后]。
- **部署流水线**：针对手动部署易出错、耗时长的问题，实现 Docker Compose 编排 + GitHub Actions 流水线；push 即自动测试、构建、发布，部署从手动 30 分钟降至 3 分钟。
```

### 简洁版（主要职责 2-3 条，压缩句式）——空间紧张时用

每条保留「模块名：问题 → 方法 → 效果」骨架，砍掉分号后的机制展开。

```markdown
### 简洁版

**CampusMarket 校园二手交易平台**（个人全栈项目）｜2024.03 – 2024.09
技术栈：React · Express · Socket.IO · MySQL · Redis · Docker

- **库存扣减**：针对高并发超卖问题，设计乐观锁 + Redis 分布式锁双层扣减方案，压测零超卖。
- **可靠消息**：针对断线重连丢消息问题，设计消息表 + 序列号 + ACK 补拉机制，重连零丢失。
- **部署流水线**：针对手动部署耗时问题，实现 Docker Compose + GitHub Actions 自动化，部署 30 分钟降至 3 分钟。
```

## 四、红线自查（生成后过一遍）

1. 每条职责是否为「**模块名**：针对……的问题，设计并实现……；（机制），（效果）」句式？没有"针对"开头问题句的条目退回重写。
2. 问题端写到"什么场景下会坏"，方法端有名字有机制，结尾有效果？
3. 每个数字有出处（代码、git、用户口述），或已是 `[待补充]` 占位符？没有代码行数、测试文件数这类码量指标？
4. 没有出现"参与/协助/了解"？没有"使用了 X"式的名词堆砌？没有「——【难点】」式标注？
5. 没有把 README 里的规划/愿景写成已实现的功能？（README 写了但代码里没有的，宁可不写）
