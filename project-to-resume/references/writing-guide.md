# 简历项目经历写作规范

## 一、输出格式（固定模板，必须严格对齐）

```markdown
## 项目经验
### 智慧教育平台 \| 后端开发
2025\-10 \~ 2025\-12
项目地址：\[shturl\.cc/xxxx\]\(shturl\.cc/xxxx\)
**项目简介**：基于 Spring Cloud 微服务架构的职业技能培训平台，包含课程学习、优惠券、多渠道支付等功能，适配企业分布式高并发场景。
**技术栈**：Spring Boot、Spring Cloud、Nacos、MyBatis\-Plus、MySQL、Redis、RabbitMQ、XXL\-JOB
核心工作与成果：
1. 通用点赞模块设计：基于 Redis 重构点赞数据结构，解耦原有业务，封装通用组件，支持全平台业务复用，提升系统拓展性；
2. 签到功能性能优化：采用 Redis BitMap 存储签到记录，大幅降低存储占用，签到查询效率提升一个数量级；
```

### 结构规则

| 行 | 规则 |
|----|------|
| `## 项目经验` | 固定一级标题，多个项目连续追加在同一个标题下 |
| `### 项目名 \| 角色` | 竖线必须转义成 `\|`；角色写"后端开发 / 前端开发 / 算法工程师 / 负责人"等，不写职级 |
| 时间行 | `2025-10 \~ 2025-12`，精确到月，波浪线转义；单个项目可不写时间 |
| 项目地址行 | 有链接才写，没有就整行省略，不要留占位 |
| `**项目简介**` | 一句：架构/技术底座 + 业务范围 + 场景特征。不写"我做了什么" |
| `**技术栈**` | 顿号分隔，6–10 个；只写成果里真正用到的，凑数会被追问 |
| `核心工作与成果：` | 冒号结尾，下面接编号列表 |
| 编号条目 | 4–6 条，每条一行，**分号结尾** |

### 转义规则

输出到 Markdown 时按示例转义，避免被渲染成表格或标题：

- `|` → `\|`
- `~` → `\~`（日期区间连接符）
- URL 中的 `.` → `\.`，链接写作 `\[url\]\(url\)`
- 其余标点（顿号、逗号、分号、括号）保持中文全角，不转义

### 条目的写法

```
<能力点命名>：<技术手段与做法>，<结果>；
```

- **能力点命名**（冒号前）：4–10 字名词短语，命名这项工作的能力标签。用"通用点赞模块设计""签到功能性能优化""高并发优惠券发放"这种，不要用"做了点赞功能""优化签到"。
- **手段**（冒号后前半）：技术选型 + 关键实现动作，用动词开头——基于 X 重构 Y、采用 X 存储、结合 X 与 Y 合并写入、使用 X 防止 Y。
- **结果**（后半）：量化优先（QPS、延迟、存储、可用性、成本）；拿不到数字就写可验证的定性收益，如"查询效率提升一个数量级""无需频繁查询数据库"。禁止空话"效果良好""显著提升"。
- **不写主语**：默认主语是"我"，不要每条加"我"。

### 排序规则

第 1 条放最能体现能力的一项（通常是最难的或有量化的）；同类项不连续放；涉及高并发/分布式/性能的优先。

## 二、句式模板

### 单条条目（40–90 字）

```
<能力点>：<动作动词> + <对象> + <技术手段>，<结果>；
```

示例：
> 签到功能性能优化：采用 Redis BitMap 存储签到记录，大幅降低存储占用，签到查询效率提升一个数量级；

### 难点三元组

```
难点（一句话现象）→ 解法（选型 + 关键动作）→ 结果（数字）
```

三元组必须连写，拆开就失去说服力。在条目里体现为"手段 → 结果"，省略难点现象；难点现象留给面试口述。

## 三、12 个字段说明（抽取阶段用，不直接输出）

| 字段 | 说明 | 抽取来源 |
|------|------|----------|
| 项目名 | 对外可理解的名字，避免内部代号 | README、PRD 标题 |
| 一句话定位 | 「给谁 + 解决什么 + 用什么方式」 | README 首段 |
| 起止时间 | 精确到月 | 用户口述、git log |
| 我的角色 | 后端开发 / 前端开发 / 负责人 / 模块 owner | 用户口述、git 贡献统计 |
| 团队规模 | 总人数 + 分工 | 用户口述 |
| 技术栈 | 语言、框架、中间件、存储、部署 | scan_project.py、配置文件 |
| 架构与数据流 | 请求从入口到存储的完整链路 | 架构图、入口文件 |
| 我负责的模块 | 具体模块名 + 边界 | 用户口述、git 提交范围 |
| 技术难点 | ≤3 个，需真正耗时解决的问题 | 用户口述、TODO/注释/issue |
| 解法 | 选型理由 + 关键实现 + 权衡 | 用户口述、代码 |
| 量化结果 | 性能、稳定性、成本、效率、业务指标 | 监控、压测报告、用户口述 |
| 业务价值 | 上线后带来的变化 | PRD 背景、复盘文档 |

其中「定位 + 业务范围」→ 项目简介；「技术栈」→ 技术栈行；「难点 + 解法 + 结果」→ 核心工作与成果条目。

## 四、动词库（按场景）

| 场景 | 强动词 |
|------|--------|
| 性能优化 | 优化、重构、压测、定位瓶颈、削峰、降延迟、提升吞吐 |
| 架构设计 | 设计、拆分、抽象、解耦、收敛、统一、落地、封装 |
| 稳定性 | 兜底、降级、限流、熔断、容灾、灰度、可观测性建设 |
| 效率/工程 | 自动化、标准化、沉淀、搭建、收敛流程、缩短交付周期 |
| 数据/算法 | 建模、清洗、特征工程、调优、评估、上线 AB 实验 |
| 业务 | 支撑、承接、覆盖、提升转化、降低资损 |

禁用弱动词：参与、协助、配合、熟悉、了解、负责相关工作、完成领导交办。

## 五、量化维度清单（按优先级）

1. **性能**：P99/P95 延迟、QPS、TPS、耗时（ms→ms）
2. **规模**：日活、数据量、日订单、存储量、节点数
3. **稳定性**：可用性（99.9x%）、故障次数、MTTR、告警量下降
4. **效率**：发布时间从 X 到 Y、人工工时节省、自动化覆盖率
5. **成本**：机器数、云账单、资源占用下降
6. **业务**：转化率、留存、GMV、资损金额、客服工单量

没有绝对值就用相对值（"下降 60%"），没有相对值就写对比基准（"较改造前"）。实在没有 → 写可验证的定性收益，或 `[待补充]`。

## 六、按岗位侧重点映射

| 目标岗位 | 前两条该写什么 | 关键词 |
|----------|----------------|--------|
| 后端 | 高并发/高可用设计、存储与缓存、分布式一致性 | QPS、削峰、幂等、分库分表、容灾 |
| 前端 | 性能与体验、工程化、复杂交互实现 | 首屏、LCP、构建耗时、组件复用率、埋点 |
| 算法/ML | 数据、特征、模型、线上效果 | AUC、召回率、AB 实验、推理耗时 |
| 数据 | 链路、时效性、质量、成本 | T+1→实时、数据一致性、任务调度、血缘 |
| 测试/DevOps | 自动化、覆盖率、稳定性、交付效率 | 自动化率、CI 时长、故障恢复、发布频率 |
| 移动端 | 包体积、启动速度、崩溃率、跨端 | 启动耗时、ANR/崩溃率、包体积 |

## 七、常见反模式

| 反模式 | 问题 | 改法 |
|--------|------|------|
| 技术名词堆砌 | 无因果，像 README | 每个技术词后面跟"为了解决什么" |
| 只写职责不写结果 | 看不出能力高低 | 每条补一个数字或可验证收益 |
| 全程"我们" | 分不清个人贡献 | 去掉主语，团队成果写"主导/牵头" |
| 写功能清单 | 像需求文档 | 改成能力点命名 + 手段 + 结果 |
| 数字无基准 | "提升 300%" 无说服力 | 补 "从 X 到 Y" |
| 条目超过 6 条 | 主次不分 | 合并同类，保留 4–6 条 |
| 过度包装 | 面试一问就穿帮 | 保留可解释的技术细节 |

## 八、可解释性自检

生成后逐条自问：
1. 这条里的每个数字，面试时能否说清测量方式？
2. 这个技术选型，能否说出放弃了什么、为什么？
3. 这个难点，能否讲出排查过程（怎么发现、怎么定位、怎么验证）？

答不上来的，要么删掉，要么降级为占位符。
